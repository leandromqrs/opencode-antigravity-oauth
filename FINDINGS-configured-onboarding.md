# Configured project onboarding

Catalog discovery can make a state-changing `onboardUser` request for the selected OAuth account when `loadCodeAssist` returns no managed project or current tier and supplies an allowed free tier. It requires exactly one default tier and that tier must be free; zero or multiple defaults never trigger onboarding. It does not invent a tier or project. Non-free tiers without a configured project are not onboarded; projectless catalog discovery remains available. Existing tiers are not onboarded again. Explicit validation-required eligibility stops onboarding.

The request uses the existing local OAuth access token, the fixed Code Assist origin, redirect rejection, bounded response bodies and per-request deadlines. The selected-account guard runs before and after onboarding and each operation poll. A pending operation is polled at most five times, five seconds apart, and only for a strictly validated relative `operations/...` name. An unfinished operation is reported as a failure; onboarding is not rolled back. A project is used only if the completed service response supplies its ID. Diagnostic messages exclude response bodies and credentials.

The operation-name format is a conservative restriction; an otherwise valid service operation name outside that format will fail rather than be followed. Tests use synthetic responses only. No live onboarding has been executed as part of this implementation.

A 60-second overall deadline bounds discovery, including account checks, requests and polling. The selected-account check cannot make an external POST atomic with a host account switch: if the switch occurs after the last check, the previous account may still be onboarded; the post-request fence prevents publishing its result for the new selection but cannot undo the remote side effect.

Catalog and onboarding HTTP requests use the local CLI user agent; the catalog client is instantiated only in the local provider branch. If model discovery returns HTTP 403 after resolving a valid project, `getCatalogFallbackProject(error)` exposes that project through a module-private weak map keyed by the original diagnostic. It is absent from error properties, messages and JSON; sanitizing or reconstructing the diagnostic loses the association. The fallback consumer must recheck the selected account before using this context and must not log the returned project. An empty 403 response remains an HTTP error.
